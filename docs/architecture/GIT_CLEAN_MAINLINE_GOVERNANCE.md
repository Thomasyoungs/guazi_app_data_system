# Git 干净主线治理规范

本规范用于保护二手车自动定价系统的稳定主线，约束人工开发和 Codex 后续开发行为。任何任务开始前，都必须先确认当前分支、工作区状态和任务影响范围。

## 1. main 分支定义

- `main` 永远代表稳定、可运行、可回滚的版本。
- 禁止直接在 `main` 上做大改。
- 所有任务必须从 `main` 拉出独立分支后开发。
- 任务完成并通过检查后，才能合并回 `main`。
- 合并回 `main` 后，`git status` 必须干净。

## 2. 分支命名

允许的分支前缀如下：

- `feature/xxx`：新增功能。
- `fix/xxx`：缺陷修复。
- `docs/xxx`：文档变更。
- `test/xxx`：测试补充或测试工具改进。
- `refactor/xxx`：不改变业务行为的结构调整。

分支名必须表达任务目的，禁止使用 `tmp`、`new`、`final`、`test1` 这类不可追溯名称。

## 3. 提交规则

- 一个 commit 只解决一个清晰问题。
- commit message 必须说明模块和目的，例如 `fix(feishu): reject duplicate message_id`。
- 禁止大杂烩提交。
- 禁止把格式化、业务改动、测试改动、临时脚本混在同一个 commit。
- 禁止提交 `.env`、真实 token、真实 `chat_id`、本地绝对路径、运行日志、缓存文件。

## 4. 合并前检查

合并前必须完成以下检查：

- `git status` 必须干净，或清楚列出仅剩的已忽略运行产物。
- 必须运行测试，并记录测试命令和结果。
- 必须输出修改文件清单。
- 必须说明是否影响定价主流程。
- 必须说明是否影响飞书。
- 必须说明是否影响 ADB。
- 必须说明是否影响手机。
- 必须说明是否影响历史任务。

如果任务涉及定价主流程、飞书网关、ADB、手机自动化、历史任务状态，必须先获得明确授权。

## 5. 证据包规则

每次任务完成后必须输出以下证据包：

- 修改文件清单。
- 新增文件清单。
- 删除文件清单。
- 测试命令。
- 测试结果。
- 风险点。
- 回滚方式。

证据包可以保存在任务说明、PR 描述或审查记录中。运行日志、截图、压缩包、临时输出默认不进入 Git 主线。

## 6. 模块边界

- `pricing`：定价系统，包括参考车选择、打分、边界确认、最终定价。
- `feishu`：飞书交互，包括消息解析、任务草稿、确认/取消、回执格式化。
- `bidding`：B 端出价系统。
- `dealers`：车商库。
- `inventory`：库存系统。
- `database`：本地数据库、迁移、数据访问。
- `common`：公共工具、通用校验、共享配置读取。

跨模块修改必须在任务说明中列出受影响模块。不得把某个模块的临时逻辑硬塞到另一个模块主流程里。

## 7. 禁止事项

- 禁止在未授权情况下调用 ADB。
- 禁止启动瓜子 APP。
- 禁止发送真实飞书消息。
- 禁止修改历史生产任务状态。
- 禁止在 `main` 上直接做大规模修改。
- 禁止为了让测试通过而删除测试。
- 禁止硬编码业务规则和本地绝对路径。
- 禁止把临时脚本混进主流程。
- 禁止绕过 V3 边界确认法修改参考车选择规则。
- 禁止修改 `全程跑通.py`、S01-S16 页面状态机、S10-S16 核心采集和定价逻辑，除非任务明确授权。

## 8. Codex 后续开发规则

Codex 执行任何开发任务前必须：

- 先运行 `git status`、`git branch`、`git log --oneline -5`。
- 如果当前在 `main` 且任务不是纯文档或治理维护，先创建任务分支。
- 修改前确认是否触碰 `pricing`、`feishu`、`bidding`、`dealers`、`inventory`、`database`、`common` 边界。
- 修改后运行 `python scripts/run_quality_checks.py`，或说明为什么无法运行。
- 输出证据包。

## 9. B 端出价系统开发起点

B 端出价系统必须从以下分支开始开发：

```text
feature/b-bid-system-design
```

不得直接在 `main` 上启动 B 端出价系统开发。
